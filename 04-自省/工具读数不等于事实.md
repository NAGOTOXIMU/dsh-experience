# 自省：工具给的"读数"，不等于事实

> 记录 2026-10-15 排查 Codex 桌面端故障时，我犯的**两个同类误判**。
> 它们不是"算错了"，而是**把某个工具在某种环境下的行为，直接当成了客观事实**。

---

## 误判一：拿 curl 的 403 当作"客户端坏了"的判据

**当时的推理**：用 curl 带客户端凭据打 `/backend-api/settings/user`、`/profiles/me`、
`/accounts/check` → 三个都 403，响应头 `Cf-Mitigated: challenge` → 结论"Codex 被 Cloudflare 挡住了"。

**实际发生的**：这个结论**当时是对的**（上游 issue 里客户端日志确实也是这几个路由 403）。
但**客户端更新恢复之后，curl 打同样三个路由依然 403**，而 `/backend-api/me` 始终 200。

**错在哪**：curl 是**非浏览器客户端**，它在这几个路由上本来就会被稳定挑战。
我观测到的其实是"**curl 会被挑战**"，然后把它外推成了"**Codex 会被挑战**"。
外推碰巧成立，但**判据本身是错的**——它会在我需要判断"好了没有"时给出假阳性。

**正确姿势**：
- 判断某个客户端的状态，**只读该客户端自己的日志**（Codex 是 `~/.codex/logs_2.sqlite`）。
- 用外部探针（curl / HTTP 请求）做辅助验证时，必须在结论里标明"**这是探针的行为，不是客户端的行为**"。
- 更狠的一条：**如果一个判据在"故障已修复"之后仍然给同样的读数，它就不是判据。** 值得回头验一次。

## 误判二：拿 glob / read 的"找不到"，当作目录不存在

**当时的推理**：`profiles\node_modules\@deepseek-ai` 用 `glob pattern="*/package.json"` 返回
*No files found*、`read <包>/package.json` 报 *not found* → 结论"这个官方插件共享池已经不存在了 /
结构变了"，并**准备去改记忆里那条"共享池约 220 个包"**。

**实际发生的**：`Get-ChildItem -Directory` 数出 **240 个条目**，全都存在。

**错在哪**：那些条目是 **junction，而且目标已被清理（悬空链接）**——
`(Get-Item <条目>).Target` 指向 `%LOCALAPPDATA%\npm-cache\_npx\<hash>\...`，
`Test-Path <Target>` 全为 False。于是：

- 链接**本身存在**（`Get-ChildItem` 看得到）
- 链接**目标不可达**（rg 默认不跟随 symlink，所以 glob/read 什么都找不到）

我看到的其实只是"**跟随链接后没有文件**"，却把它读成了"**条目不存在**"。
差一点就把记忆里**正确**的一条改成错的。

**正确姿势**：判断一个 node_modules 目录"有没有内容"，两步复核：
`Get-ChildItem`（列条目）→ `(Get-Item <条目>).Target` + `Test-Path <Target>`（验目标）。

## 抽象出来的共同点

```
工具输出  ──[解释层]──>  事实
```

我漏掉的正是中间那层。两次都是"读数 → 直接跳到事实"，跳过了：

1. **这个工具在这件事上的行为是什么**（curl 会被挑战；rg 不跟随 symlink）
2. **读数有没有别的解释**（客户端正常了 curl 也照样 403；条目在但目标没了）
3. **对照试验**（同样条件下换个工具 / 换个对象，读数会不会变）

**一条可操作的纪律**：

> 当某个读数要用来支撑一个"坏了 / 不存在 / 不可用"的结论时，
> 先用**另一种工具**或**另一种路径**复现一次；
> 复现不了，就把它写成"某工具的读数"，而不是"事实"。

这也解释了为什么"**别用自己脚本的打印当成功证据**"（`git show :<path>`、`$LASTEXITCODE` 那几条）
是同一类纪律——**证据链里最薄弱的一环，往往是对工具行为的想当然。**
