# 自省：本次协作中我的六类误判

| 字段 | 值 |
|---|---|
| **验证情况** | 已证实（每一条都有当时的输出为证） |
| **期间** | 2026-10-06，DSH 桌面版能力改造全程 |
| **为什么要写** | 标出"我的直觉在哪些地方不可靠"。不写下来，下次一定重犯 |

> 这次协作里我给出的**错误结论比正确结论更早、更自信**。
> 每一条都是"看起来有证据、其实证据指向别处"。

---

## 误判 1：把"历史副本"当成权威

**我当时做了什么**
看到 `<DSH 目录>\apps\dsh-desktop\home\` 里有 `AGENTS.md`、`profiles\desktop`，
就认定桌面版的 `DSH_HOME` 是它。

**真正的事实**
主进程命令行明确写着 `C:\Users\<你>\.dsh\profiles\desktop`。
`apps\dsh-desktop\home` 是**已停用的历史副本**（最后活动 2026-09-18）。

**为什么会错**
"目录结构很像"就当成事实，**没有去读最直接的证据（进程命令行）**。

**教训**
判断"哪个目录在生效"要看**运行中的进程参数**，不要靠目录形态推测。

---

## 误判 2：混淆"工作区里的模板"与"真实运行态"

**我当时做了什么**
基于 `apps\dsh-desktop\home\profiles\desktop\package.json` 报告："大量插件是 `absent`、
记忆插件根本没启用、这个 harness 很简陋"。

**真正的事实**
那是模板副本的状态。真实运行环境里 base 已含全套官方能力（约 220 个包），
DSH 是 `0.2.0-rc.2`，**相当新**。

**为什么会错**
拿"另一个目录的配置文件"去推断"当前运行环境的实际状态"。

**教训**
配置文件 ≠ 运行态。**要判断运行态就用运行时探测工具**（`cordis_inspect_*`）。

---

## 误判 3：把 `inactive` 当成"正常装载"

**我当时做了什么**
`Config listConfigs` 显示 memory 等条目 `status: inactive`，
我看到 `dsh-tool-todo` 等正常工作的条目也是 `inactive`，就下结论"这是正常状态"。

**真正的事实**
`inactive` 是"没跑起来"。真正的状态字段是 `plugin_manager` 的 `fiberPhase`
（`active` = 已实例化，`null` = 未实例化）。memory 的 `fiberPhase` 是 `null`。

**为什么会错**
用"存在同类现象"代替"验证该现象的含义"。
`dsh-tool-todo` 确实工作正常 —— 但那不能证明 `inactive` 就是正常的，
只能说明**我读的那个字段不表示状态**。

**教训**
**别用类比代替验证**。字段含义要去查它的定义或换一个能区分的观测。

---

## 误判 4：把自己的 PowerShell 子进程认成"新的 host 进程"

**我当时做了什么**
用 `Get-CimInstance Win32_Process | Where-Object CommandLine -match 'dsh-desktop-host'`
去认 host 进程。结果匹配到了**我自己那条 PowerShell 命令的子进程**
（它的命令行里包含我正在执行的脚本文本，而脚本里就写着 `dsh-desktop-host`）。
于是我宣布"应用已重启，但插件仍未生效 ⇒ 重启没用"。

**真正的事实**
当时**根本没重启**（host 仍是 PID 22668 / 19:00:35）。
后来才发现真正的判据是时间戳：patch mtime 比进程启动晚 116 分钟。

**为什么会错**
用一个**会匹配到自己**的模式去找进程；而且看到"启动时间很新"就采信了，
没有交叉验证（例如对比端口、对比父进程）。

**教训**
- 用命令行做模式匹配时，**必须排除当前命令自身的进程**。
- 判断"是否重启"要**比时间戳**，不要靠"看到了新 PID"。

## 误判 5：工具报错时，跳过证据直接下"根因"结论

两次同类错误：

**(a) "npm 上没有 0.1.x 那些版本"**
依据：`pnpm` 报 `NO_MATCHING_VERSION`、下载报 `UND_ERR_DESTROYED`。
事实：核对 registry 后，`0.1.5-rc.3`、`0.1.6-alpha.1`、`0.2.0-rc.2` **全都在**。
那两条只是**代理抖动 + registry 解析异常**。

**(b) "`@ningbainb` 包无处可指、版本不兼容"**
依据：看到 peer 要求 `^0.1.x` 而本机是 `0.2.0-rc.2`。
事实：实测 `import` 三个包**全部成功**，host 产物字节数正常（32161 / 60692 / 13553）。

**为什么会错**
把"工具的报错信息"直接当成"客观事实"，而报错信息本身可能有别的原因
（网络、配置、注册表）。而且**没有做那个能一锤定音的验证**（直接 import / 查 registry 版本列表）。

**教训**
报错信息是**线索**，不是**结论**。下根因前必须做一次独立验证。

## 误判 6：把"单个观察"总结成"规律"

**我当时做了什么**
看到部分插件失败后，归纳说："带 `config:` 的 insert 条目会被禁用。"
紧接着就自己发现了反例（`find-dsh-plugin` 没有 `config` 也被禁），却说"规律不成立"，
却**没有继续找真正的一致差异**。

**真正的一致差异其实就在数据里**：`dsh.client` 的有无（见失败模式文档）。

**为什么会错**
归纳时**样本不够就下结论**，且发现反例后**只是撤回结论、没有继续追问**。

**教训**
出现反例时，正确动作不是"撤回规律"，而是**把反例也放进表格，直到找到真正的判别维度**。

## 这六条的共同根因

**都是"看到现象 → 立刻给解释"，而不是"看到现象 → 设计一个能区分的观测 → 再解释"。**

在这种没有文档、机制不明的环境里，这个习惯尤其危险：
每个现象都有好几种合理解释，而**我倾向于选那个最先想到的**。

## 可操作的修正（已固化到行为准则）

1. **先找"决定性观测"**：能一次区分两种假设的那个实验。
   例如判断"是不是没重启"→ 比时间戳；判断"是不是加载失败"→ 直接 `import`。
2. **报错信息只当线索**，下根因前做一次独立验证。
3. **归纳要列完整表格**，出现反例时扩充维度，而不是撤回结论。
4. **区分"配置文件"与"运行态"**，判断运行态一律用运行时探测。
5. **做进程/命令行匹配时排除自身**。

- 每轮把结论**推送到远端仓库**，所以即使本地清理，证据仍可追溯。
