# 失败模式：插件装了却不激活

| 字段 | 值 |
|---|---|
| **证据等级** | 已证实（6 个案例全部一致） |
| **适用版本** | DSH `0.2.0-rc.2`，desktop profile |
| **发现日期** | 2026-10-06 |
| **复核方式** | 见文末"复现方法" |

---

## 症状

在 `profiles\<profile>\cordis.patch.yml` 里用 `- insert:` 挂载第三方插件后：

- `plugin_manager action=list_plugins` 显示该条目 `enabled: false`、`fiberPhase: null`
- 插件本应注册的 Service 在 `Service listService` 里查不到
- 插件本应提供的 Tool 在模型工具列表里没有

**关键迷惑点**：`plugin_manager action=set_plugin enabled=true` 会返回
`{"changed":true,"application":"overridden"}` 并往 patch 写入 `- id: x / disabled: false`，
**但运行时状态丝毫不变**。这会让人误以为"配置对了，只是需要重启"。

## 根因

**插件的 `package.json` 是否声明 `dsh.client`（浏览器半边）。**

在 desktop profile 中，**不声明 `dsh.client` 的纯 host 插件无法被激活** ——
即使它自带了 `cordis.patch.yml`、即使 `packageDir` 解析正确、即使手工 `import` 能成功。

## 证据

| 条目 | `dsh.client` | enabled | fiberPhase |
|---|---|---|---|
| `@linxin666/dsh-client-ui-skill-explorer` | ✅ | true | **active** |
| `dsh-plugin-ops-bundle` | ✅ | true | **active** |
| `dsh-plugin-marketplace` | ✅ | true | **active** |
| `dsh-glass-tweaks` | ✅ | true | **active** |
| `@ningbainb/dsh-user-scope` | ❌ | false | null |
| `dsh-find-plugin` | ❌ | false | null |
| `dsh-session-recall` | ❌ | false | null |
| `@ningbainb/dsh-memory` | ✅（反例） | false | null |
| `@ningbainb/dsh-personal-prompt` | ✅（反例） | false | null |

**决定性观察**：`dsh-session-recall` 在**未重启**的活进程里刚装好就是 `false`；
`set_plugin` 后仍是 `false`。而另外 4 个**重启过**也仍是 `false`。
⇒ **"需要重启"这个解释是错的**，新插入的条目从一开始就不会被激活。

## 已排除的假设（都做过实测）

| 假设 | 排除依据 |
|---|---|
| 包损坏 / 加载失败 | 全部包实测 `import` 成功，导出 `apply` / `inject` / `name` |
| junction / node_modules 失效 | host 产物可达，`packageDir` 正确解析 |
| YAML 语法错 | 无 tab 缩进、id 唯一、YAML 合法 |
| patch 内被禁用 | patch 原本没有任何 `disabled` |
| 版本不兼容 | peer 声明是旧范围，但 host 部分实测可加载 |
| `config:` 字段导致 | 无 `config:` 的 `find-dsh-plugin`、`session-recall` 一样失败 |
| 需要重启 | 已推翻（见上） |

## 处置

1. **装之前先看** `package.json` 里有没有 `dsh.client`：
   ```powershell
   (Get-Content "<profile>\node_modules\<包名>\package.json" -Raw | ConvertFrom-Json).dsh |
     ConvertTo-Json -Depth 4
   ```
   没有 `client` ⇒ **预期它不会生效**，别浪费时间。
2. **装完立刻验证**（不要等重启）：
   ```
   plugin_manager action=list_plugins   → 看 fiberPhase
   ```
   `active` 才算成功；`null` 就是这条失败模式。
3. **不要反复试 `set_plugin`** —— 它对这个症状无效，只会往 patch 里堆无用条目。
4. **替代方案**：优先选声明了 `dsh.client` 的同类插件。

## 未收敛的部分（诚实标注）

`@ningbainb/dsh-memory` 与 `dsh-personal-prompt` **声明了** `dsh.client` 却仍失败，
所以"纯 host"不是充分解释。补充假设（**未证实**）：

> 它们的客户端 peer `dsh-client-store`、`dsh-client-ui-slots` 在本机共享池**不存在**，
> 可能因此导致 client 半边加载失败，进而整条 entry 被判为不可用。

尚无日志证据支持（host 进程输出被 GUI 捕获，`~/.dsh/logs` 为空）。

## 反例（看似同类其实不同）

- **`Config listConfigs` 说 `absent` 不代表没装** —— 它读的是**会话启动时的快照**，
  新加的条目在快照里永远不存在。判断状态必须用 `plugin_manager`。
  详见 [工具数据源不一致](工具数据源不一致.md)。
- **沙箱里 `import` 成功 ≠ 装到 profile 里能生效** —— 前者只验证模块可加载，
  后者还要过 Cordis 的条目激活。评估阶段 5 个候选全部 `import` 成功，
  但装进 profile 后 `session-recall` 依然不激活。

## 复现方法

```
# 1) 真实状态（必须用 plugin_manager，不能用 Config）
plugin_manager action=list_plugins offset=<n> limit=<m>
   → fiberPhase: active = 已实例化；null = 未实例化

# 2) 该包是否声明 dsh.client
(Get-Content "<profile>\node_modules\<包名>\package.json" -Raw | ConvertFrom-Json).dsh

# 3) 插件应注册的服务是否真的在
cordis_inspect_query platform=host provider=Service method=listService
   input={"service":"<服务名>"}
   → 报 "no catalogued Service named X" 即未注册

# 4) 顺带确认"是不是没重启"这个混淆项
#    patch mtime 晚于 host 进程 StartTime ⇒ 本次启动没加载过这些配置
Get-CimInstance Win32_Process -Filter "Name='DeepSeek Harness.exe'" |
  Where-Object { $_.CommandLine -match 'dsh-desktop-host\\lib\\index\.js' } |
  ForEach-Object { (Get-Process -Id $_.ProcessId).StartTime }
(Get-Item "<profile>\cordis.patch.yml").LastWriteTime
```

## 时效性警告

DSH 迭代很快，这可能是个会被官方修掉的缺陷。
**复核方式**：按上面的复现方法跑一遍；若纯 host 条目开始出现 `fiberPhase: active`，
说明已修复，本文件应改标 `已失效`。
