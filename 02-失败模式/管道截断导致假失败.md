# 失败模式：`| Select-Object -First N` 让子进程"失败"，退出码变成 -1

| 字段 | 值 |
|---|---|
| **证据等级** | 已证实（同一条命令，两种调用方式对照实测） |
| **适用** | Windows PowerShell（5.1 实测；任何"提前关闭读端"的管道行为同理） |
| **发现日期** | 2026-10-07 |
| **复核方式** | 见文末"复核方法" |

---

## 症状

联网寻源脚本输出"看起来完全正常"的 25 行结果，但 `$LASTEXITCODE` 是 **-1**：

```
& python E:\Tools\gh-dsh-search.py --github-only | Select-Object -First 35
  ...（正常的候选列表）...
LASTEXITCODE=-1
```

差一点据此判定"脚本坏了 / 联网失败"，而它其实**完全正常**。

## 根因

`Select-Object -First N` 凑够 N 行后会**关闭管道读端**。上层还在往 stdout 写的
Python / Node 进程随即吃到 **BrokenPipe**，于是以非零码退出（Python 里是 -1）。

**"失败"的是管道被提前关掉这件事，不是被执行的命令。**

## 证据（同一条命令，只改输出方式）

| 调用方式 | 退出码 |
|---|---|
| `... --github-only \| Select-Object -First 35` | **-1** |
| `... --github-only > 文件`，再读文件 | **0** |

第二次重跑输出内容一致，且无任何 Traceback / 报错关键词。

## 处置

- **要判断退出码，就别截断它的 stdout**：重定向到文件，或先拿完整输出再筛。
- 确实只想看前 N 行时，把"截断"放到子进程结束之后：
  `... > out.txt` 然后 `Get-Content out.txt -TotalCount 35`。
- 脚本侧可捕获 `BrokenPipeError` 后静默退出 0（Windows 上 `SIGPIPE` 不可用，
  只能用异常处理）。

## 反例 / 易混淆点

- **不是"Python 脚本写错了"**：同一条命令不截断就是 0。
- **不是"看退出码这个做法错了"**：看 `$LASTEXITCODE` 依然正确，
  但要意识到**同一个命令在不同调用方式下会给出不同退出码**。
- 与 [工作区权限阻塞](工作区权限阻塞所有命令.md) 的区别：那种情况命令**根本没启动**；
  这里是命令跑完了、结果也对，只是退出码被管道副作用污染。

## 一条更普遍的教训

"命令成功还是失败"会同时受**三层**影响：命令自身、shell 的管道行为、harness 的捕获方式。
下判断前先确认这三层都没动手脚。

## 复核方法

```powershell
$out = "$env:TEMP\pipe-probe.txt"
& python E:\Tools\gh-dsh-search.py --github-only | Select-Object -First 5
"截断时   LASTEXITCODE=$LASTEXITCODE"          # 预期 -1
& python E:\Tools\gh-dsh-search.py --github-only > $out
"不截断时 LASTEXITCODE=$LASTEXITCODE"          # 预期 0
```
