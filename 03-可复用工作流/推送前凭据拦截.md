# 可复用工作流：给 Git 仓库加推送前凭据拦截

| 字段 | 值 |
|---|---|
| **验证情况** | 已证实（拦截逻辑用注入测试端到端验证；实测命中真实的配置备份） |
| **适用版本** | 任意 Git 仓库（含公开/私有远端）；示例脚本用 Windows PowerShell 5.1 实跑 |
| **用途** | 在 commit **之前**拦下凭据与隐私红线，避免秘密永久进入 Git 历史 |

---

## 为什么必须在 commit 之前

凭据一旦被提交，就留在了 Git 历史里。**事后删文件不等于删除历史** ——
旧内容仍以 blob 形式保存在 `.git` 中，任何人 `clone` 后都能翻出来。
真正清理需要重写全部历史并强推，还要通知所有协作者重新克隆；若已推到公开远端，
第三方缓存与抓取可能已经留存，**无法召回**。

所以拦截点必须放在 `git add` 之后、`git commit` **之前**。

另一个更隐蔽的陷阱：**"推送后清理本地副本"的流程会制造假安全感** ——
本地文件消失了、看起来干净了，但秘密已经躺在远端历史里。
备份文件、配置快照、数据库导出这类产物天然带凭据，必须有机制在入库前挡住。

---

## 设计要点

### 1. 分级：硬拦截 vs 提醒

误报会让拦截机制被绕过，所以分成两级：

| 级别 | 判据 | 处置 |
|---|---|---|
| **硬拦截** | 100% 可信的形态（见下表） | 中止提交 |
| **提醒** | 形似但可能是普通代码 | 只打印，不阻断 |

硬拦截的形态（几乎不会误伤）：

- API key：`sk-` 后跟 20 位以上字母数字
- GitHub token：`ghp_` / `gho_` / `ghu_` / `ghs_` / `ghr_` / `github_pat_` 前缀
- 私钥内容：`-----BEGIN ... PRIVATE KEY-----`
- AWS Access Key：`AKIA` + 16 位大写字母数字
- **敏感文件名**（不读内容也拦）：`auth.json`、`credentials*`、`.env*`、`id_rsa`、
  `*.key` / `*.pem` / `*.pfx` / `*.p12`、`*.db` / `*.sqlite`、`*.bak` / `*.old`

**关键**：泛型规则（`token = "<长串>"`）误报率高 —— 同一行可能只是类名、
CSS 变量名或常量。这类一律降级为「提醒」，或加二次判定（是否含数字、大小写混合、
无 `-` / `_` 分隔符、长度 ≥ 24）。实践中的数据：某插件代码里 11 处 `token` 匹配
全部是 18 位类名，**没有一处是真凭据**。

### 2. 输出必须打码

扫描器会打印命中的内容，**绝不能把整串秘密写进日志或终端历史**。
只留前 6 位 + `***REDACTED***`。

### 3. 公开仓库额外加隐私红线

对公开远端，除凭据外还应拦截：

- 真实用户目录路径（`C:\Users\<真名>`、`/home/<真名>`）
- 用户名、邮箱、账号等个人身份标识
- 本机专属路径（自定义盘符/工具目录）

**注意豁免规则**：文档里合法使用占位符时（如 `C:\Users\<你>`）不应误拦，
即"尖括号包裹的占位符"要放行。

### 4. 留逃生开关

必须有 `-SkipSecretScan`（或等价开关），否则一旦误报，
整个推送流程被卡死、只能去改脚本。跳过时打提示，但不静默。

## 最容易踩的坑：扫描器"报 OK 却什么都没检查"

**第一版实现用了 `git show HEAD:<path>` 去读暂存区内容 —— 这是错的。**
待提交的新文件在 HEAD 里并不存在（git 返回 **128**；首次提交时更是没有 HEAD）。

```powershell
# ✗ 错的：待提交的新文件不在 HEAD 里
git -C $repo show ("HEAD:" + $RelPath)
# ✓ 对的：读暂存区
git -C $repo show (":" + $RelPath)
```

**为什么这个 bug 特别危险**：读取失败被静默吞掉后，扫描器输出
「已检查 **0**/N 个文件」并打印 OK —— **看起来通过了，其实一个文件都没读**。
如果不看那个计数、不做注入测试，就会一直以为保护生效。

因此两条硬要求：

1. **报告里必须打印"真正读到的文件数"**，而不是只看"有没有报错"；
2. **必须做端到端注入测试**：造一个含假凭据的文件暂存进去，确认它**真的被拦住**。
   语法检查通过、函数存在，都不等于逻辑生效。

验证用的假样本不要用真凭据；测完清理掉测试仓库。

## 实现骨架（PowerShell）

```powershell
# 1) 暂存 -> 取文件列表
git add -A
$files = @(git -C $repo -c core.quotepath=false diff --cached --name-only |
           Where-Object { $_ })

# 2) 在 commit 之前扫描
$r = Invoke-SecretScan -Repo $repo -Files $files
Show-SecretScanReport -Result $r -RepoName 'repo'
if ($r.Blocked) { throw "发现 $($r.Hard.Count) 处硬问题，已中止（未提交、未推送）" }

# 3) 通过后才提交
git commit -q -m $msg
git push
```

读取单个暂存文件时，用临时文件承载比用管道捕获更稳（避免把逐行输出拼成数组后
丢失换行信息）：

```powershell
& git -C $Repo -c core.quotepath=false show (":" + $RelPath) 1>$tmp 2>$null
if ($LASTEXITCODE -ne 0) { return $null }        # 读不到就跳过，但计数要能反映出来
return [System.IO.File]::ReadAllLines($tmp, [System.Text.Encoding]::UTF8)
```

用 `ReadAllLines` 而不是 `ReadAllText`，后续按行处理时不必再手动切分、也不受行尾差异影响。

## Windows / PowerShell 实现坑（都实测过）

| 坑 | 表现 | 处理 |
|---|---|---|
| **`List[byte].AddRange(byte[])` 抛类型异常** | `无法将参数 collection 转换为 Object[]` | 想按字节精确替换某一行时，别用 `AddRange`；改用**文本级按行处理** + `WriteAllText` |
| **`.ps1` 必须带 UTF-8 BOM** | PowerShell 5.1 按 GBK 解码无 BOM 的 UTF-8，报**假语法错误**或中文乱码 | 写完显式写回 BOM，并用 **5.1 实跑一次**验证（用 7.x 测不出这个问题） |
| **工作区外目录写入被拒** | `Access to the path ... is denied` | 在工作区内生成 → 校验（BOM + 语法）→ 用**带自动回滚**的部署脚本一次性拷贝 |
| **`.NET` 写文件失败是非终止错误** | 脚本照样打印"已更新"，文件其实没变 | 成功判定必须来自**独立读取 + 哈希比对**，不能信同一段脚本的自述 |
| **`Compare-Object` 做 diff 看不到内容** | 只回 `=>` / `<=` 符号 | 看内容差异用 `git diff --no-index <a> <b>` |

**部署脚本的回滚模式**（值得照抄）：备份原文件 → 复制 → 校验（哈希一致 + BOM + 语法 +
关键内容存在）→ **任一失败就自动还原**。这样即使部署中断也不会留下半成品。

## 顺带发现：凭据真实形态的分布

扫描一台机器上所有文件后，命中的往往不是你以为的那些：

- **软件自带的测试证书/密钥**（Python、Qt、浏览器引擎的测试数据）占大头，属噪音
- **`*.pem` 私钥** 可能来自数据库客户端、SSH 组件
- **真正该警惕的**是"用户自己按服务建的明文凭据目录"：按服务分子目录、
  常伴随 `- 副本` 后缀的**冗余副本**

关于冗余副本的判断要**用哈希，不要看文件名**：文件名带"副本"的通常是重复，
但**去掉后缀的那份不一定就是同一个**——同一目录下可能并存两份**不同的** key
（例如一份旧 key、一份刚生成的新 key）。误判成"重复"会导致删错东西。

## 配套措施（比脚本更重要）

- **已进入过副本的凭据，只能轮换**。被终端、编辑器、会话记录、日志、截图
  读过的 key，就不再是秘密 —— 删文件无法回收，正确处置是**在服务端作废重发**。
- **账号口令**类凭据不可撤销，泄露后**只能改密**。
- 把凭据从明文配置里挪到**环境变量引用**（多数工具支持指定"变量名"而非直接填值），
  至少让明文不落在配置文件中。
- 明文凭据目录至少做两件事：**收紧 ACL**（阻断继承、只留本人）、
  **放一个说明文件**写明"这是敏感目录、别同步云盘、别提交进任何仓库"。

## 时效性警告

拦截规则基于凭据的**格式前缀**。服务商若改变 key 形态（如新增前缀、
改用非字母数字字符），规则需要同步更新。定期用真实的备份/配置文件试跑一次，
确认扫描器仍能命中。
