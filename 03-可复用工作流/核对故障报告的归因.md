# 核对一份故障报告的归因（以「MSIX = 万能背锅侠」为例）

| 字段 | 值 |
|---|---|
| **验证情况** | 已证实（逐条对照本机实测核过） |
| **适用版本** | DSH `0.2.0-rc.2` 桌面版，Windows 11 Build 26200 |
| **整理日期** | 2026-10-07 |

---

## 背景

一份故障报告把「AI Agent 频繁在终端报错、浪费大量 Token 试错」归因于
**MSIX 版 PowerShell 7**（装在 `C:\Program Files\WindowsApps\`），并列了三条：

1. 安装包类型错误（MSIX 而非 MSI）→ 「最核心隐患」
2. 沙箱受限令牌与 Schannel 凭证冲突（`SEC_E_NO_CREDENTIALS`）
3. 终端外壳与内核版本混淆

## 逐条核对结果

| 报告说法 | 本机实测 | 判定 |
|---|---|---|
| pwsh 在 `WindowsApps\...` | 路径确实是它 | ✅ 成立 |
| 是 winget 装的 MSIX | installer 类型 `msix`，包体 URL 指向 GitHub Releases | ✅ 成立 |
| MSI 标准位置不存在 | `C:\Program Files\PowerShell\7\pwsh.exe` = False | ✅ 成立 |
| WindowsApps 不可读、排查黑盒 | `icacls` 报 `Access is denied` | ✅ 成立 |
| **「路径硬编码失效 → Agent 找不到 pwsh → 无效重试」** | ✗ 解析顺序是「PS7 标准位置 → **扫 PATH** → 5.1 兜底」，MSIX 靠 `%LOCALAPPDATA%\Microsoft\WindowsApps\pwsh.exe` 别名**照样命中**。装完后 pwsh 调用**零失败** | ❌ **不成立** |
| **「MSIX 的 AppContainer 层嵌套 DSH 沙箱导致权限边界异常」** | ✗ 无证据；实测 PS7 在受限令牌下正常执行 | ⚠️ **未证实**（未做穷尽测试） |
| 受限令牌下 `curl.exe` 的 HTTPS 失败（Schannel 取不到凭证） | 记忆中确有此项记录（来自历史会话，**本次未复测**）；成因（SSPI 需访问凭证存储）技术上成立 | ✅ 成立 |
| 终端外壳与内核版本解耦（5.1 与 7 并存） | 两者确实并存；Windows Terminal / VS Code 的 shell 由各自 profile 决定，与"装了 pwsh 7"无关 | ✅ 成立（但**不影响 DSH**，DSH 自己解析 shell） |

## 同一时期真正拖慢效率的三件事（都与 MSIX 无关）

| 真凶 | 症状 | 处置 |
|---|---|---|
| **PowerShell 5.1 的编码/引号/BOM** | 无 BOM 中文脚本报**假语法错误**、`gh` 参数被拆坏、UTF-16 输出乱码 | 升级 PS7 后消失 |
| **会话工作区 ACL 授权失败** | `SetNamedSecurityInfoW failed (Win32 5)` → **任何命令都起不来**（只读命令也一样） | 见 `02-失败模式/工作区权限阻塞所有命令.md` |
| **DSH 给工作区设低完整性标签** | 装在工作区里的 Electron 应用秒退（`0x80000003`、**零日志**） | 见 `02-失败模式/低完整性标签污染程序.md` |

## 可复用的核对方法（真正要带走的部分）

1. **把「事实」与「因果」分开核。**
   事实（路径在哪、什么安装类型、目录能不能读）**可以直接查证**；
   因果（"所以导致 X"）**必须要有对照实验**，不能由事实推演出来就算数。

2. **先找反证，而不是先找支持。**
   问一句："**如果这个原因成立，什么现象必须出现？出现了吗？**"
   本例中：若真是"路径找不到 pwsh"，那 pwsh 调用**必然报错** —— 实测零失败，推论当场破产。

3. **控制变量是唯一有说服力的证据形态。**
   报告里第 ② 条的证据链（直连 HTTPS 失败 → TCP CONNECT 200 → 明文 HTTP 204 → Node.js 直连 200）
   就是范本：每一步只动一个变量，把"网络问题"逐层排除掉。

4. **区分「不好查」与「不能用」。**
   前者是**诊断体验**，后者才是**功能故障**。MSIX 的问题全在前者。

5. **警惕"最底层、最技术"的那个原因。**
   它看起来最能解释一切，但往往不是真正拖慢你的那个 —— 本例真凶是上古的 PowerShell 5.1 行为。

## 一句话结论

> **MSIX 的问题是"不好查"，不是"不能用"。**
> 换成 MSI 版能解决**诊断不便**（落回标准路径、权限可读、成为 shell 解析的第一候选），
> **但别指望它解决"命令报错"** —— 那属于另外两层。
