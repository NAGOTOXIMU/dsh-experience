## 1. 用户想要什么（原始诉求）

> "把这个文件夹初始化成git项目,并推送到github上"

两个**无法从环境推断**的点：仓库名、公开还是私有——因为 `E:\git` 是**空文件夹**，
没有任何内容能提示用途。于是问了这两个问题（只问一次），用户选：`sandbox` + 私有。

## 2. 发生了什么

| 阶段 | 结果 |
|---|---|
| 侦察 | **卡死**：`SetNamedSecurityInfoW failed (Win32 5): grantWrite(E:\git)`，任何命令都起不来 |
| 修权限 | skill `diagnose-windows-sandbox-acl` 一条命令修好（病灶：目录缺 `WRITE_OWNER`） |
| `git init -b main` | 成功（本机全局 `init.defaultBranch` 已是 `main`） |
| 初始提交 | `b9124c2`，2 个文件：`README.md`、`.gitignore` |
| `gh repo create ... --push` | 仓库建成、`origin` 配好，但内置的 push 步骤失败（沙箱） |
| 受限模式直接推 | 失败：schannel `SEC_E_NO_CREDENTIALS`；换 openssl 又撞命名管道 |
| 放宽一次后推 | **成功**，远端 `main` = `b9124c2` |
| 验证 | `gh repo view` → `PRIVATE`；`gh api .../contents` → 恰好两个文件 |

## 3. 留下了什么

- 两条可复用失败模式 → [受限沙箱下git推送失败](../02-失败模式/受限沙箱下git推送失败.md)、
  [工作区权限阻塞所有命令](../02-失败模式/工作区权限阻塞所有命令.md)
- **本机操作性结论**：受限模式下凡 `git push` 都要单独放宽一次；
  而 `gh api`、`gh repo create`、`gh repo edit` 等 Go 侧调用**不受影响**，可继续在受限模式用。
- 权限恢复备份（用户选择保留在本地作回滚安全网）：
  `E:\DSH-Archive\acl-recovery-20261006\`

## 4. 事后回看

- **授权问询问得值**：文件夹为空时，仓库名与可见性无法推断，
  猜错的代价是改仓库名、重建仓库或撤回公开。两个问题一次问完，成本很低。
- **两次"看起来像配置问题"的故障，根因都在沙箱**：
  `SEC_E_NO_CREDENTIALS` 像是 TLS/证书配置问题，`couldn't create signal pipe` 像是 git 安装损坏，
  实际都是受限令牌。教训与 `04-自省/` 同类：**报错文本只指方向，不指根因**。
- 判别手法这次的用法值得固化：**同一分钟跑一个同目标、不同实现的命令**（`gh api` 对 `git push`），
  一次就把"网络/凭据/仓库"三类假设全部排除掉。
